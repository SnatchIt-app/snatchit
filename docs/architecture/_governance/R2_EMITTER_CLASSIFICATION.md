# R2 — Producer Emit-Clause Classification (OR-14, owner-signed)

**Drafter:** Agent C (read-only). 2026-08-29.
**Ruling applied:** OR-14 R2 — exactly TWO emission behaviors. (1) **REQUIRED-RAISING** (`notify.emit_event_required`): the producer transaction MUST fail if the envelope is unwritable — used only where another required invariant (Wallet credential staleness, custody visibility, key-revocation propagation) depends on the envelope. (2) **BEST-EFFORT** (`notify.emit_event` / `notify.enqueue`, non-raising): pure notices; failure never aborts money/state. Every producer explicitly classified; no default; no third behavior.
**Sources:** ODR2_BUILD_CONSEQUENCE_MAP.md §1/§7/§8 · ODR3_GATE_P_REDUCED_SCOPE.md §1/§2/§8 (N3 pass) · PHASE_2_NOTIFICATIONS_SPEC.md §0.3/§2.2 (post-N3 catalogue) · PHASE_2_APPLE_WALLET_SPEC.md §6.3/§6.4/§7 · PHASE_2_RPC_FUNCTION_CONTRACTS.md §17.24 + producer contracts (§4.4, §6.3, §7.1–7.5, §9.4, §10.3, §11.2–11.4, §17.1–17.4, §17.7, §17.10a, §17.14, §20.2.4, §20.4.1/2, §20.7.1–20.7.6, §17.23).

**Stated once, applies to every REQUIRED row:** where a fact drives BOTH a Wallet update AND a notice, the **envelope** is REQUIRED; the notice leg stays best-effort **at delivery** (channel resolution, adapters, dead-letter) — delivery is a drain-time property of `drain_outbox`/`claim_deliveries`, not an emit property of the producer. A REQUIRED classification never makes a push or email delivery load-bearing.

**Stated once, applies to every DB row:** the envelope is written **last within the producer's transaction, after every money/custody row**, under the aggregate's existing row lock (§17.24) — same-txn for both classes; the classes differ only in what happens when that write fails (abort vs warn+commit).

## Notes and flags

1. **Genuinely out of scope, reported not classified:** the five door notices (`DOOR:1577–1581`, events #37–#41 copy) and `kernel.sweep_expired_door_overrides`' contracted "emits notifications" have **no catalogued type key** (ODR-3 §1.1 reported gap). They cannot be classified until keyed; when keyed they are notices → BEST-EFFORT on their face. They do not break the UNCLASSIFIED=0 count because they are not IN types and not ODR-2 facts.
2. **One divergence from the drafting instruction, flagged for review:** the instruction's canonical REQUIRED parenthetical includes `wallet_pass_available`. ODR-2 §8's defect statement names **#17 and #28** (the `credential_version`-bump triggers) and nothing else; `wallet_pass_available` drives no Wallet update — it is emitted *by* the pipeline after signing, class ON, with the catalogue's explicit inference that suppression costs nothing. Under OR-14's own test ("REQUIRED iff a required invariant depends on the envelope") it is BEST-EFFORT, and row 30 classifies it so. If the owner intends it REQUIRED, that is a new bit: the `credential-sign` edge fn would have to fail pass issuance when the notice cannot be written — which inverts WALLET's "Wallet can never block" posture.
3. **N-A30 must be re-scoped, or it re-breaks the ruling:** N-A30 asserts "every producer trigger body contains its own `EXCEPTION WHEN OTHERS`" — applied to a REQUIRED producer, that second swallow layer would eat the raise and silently reproduce the ODR-2 §8 defect. N-A30 survives for BEST-EFFORT producers only; the six REQUIRED producers must NOT wrap the emit in an exception handler (asserted structurally by T-RPC-NOTIFY-08 below).
4. **The mandatory-class ≠ emit-class point, once:** notification `MANDATORY` (undisableable delivery) and REQUIRED-RAISING (emit aborts) are orthogonal. 21 of 24 BEST-EFFORT rows carry MANDATORY types; none of that changes the emit class — R3's "raise iff mandatory" was rejected in ODR-2 §8 precisely because the Wallet consumers have no notification class.
