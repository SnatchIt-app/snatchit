## 2. The "Paying with" card / Stripe FlowController proposal — DO NOT BUILD as proposed

What it would change: today the checkout is `initPaymentSheet` → `presentPaymentSheet` (collects and confirms in one native step) → `finalizePurchase` (CheckoutNative.tsx:5–6, :365, :507); `payControl` orders the states around that single step (confirming → finalizing → checking; hold-lost and expiry-margin outrank readiness; `statusUnknown` never offers Pay) and A-02 re-runs setup when the server total changes (:399, :703–707). FlowController splits collection from confirmation (`presentPaymentSheet` collects the method, `confirmPaymentSheetPayment` charges later), which inserts a client-held interval between "method chosen" and "charge" during which: the hold can pass `PAY_EXPIRY_MARGIN_MS` (the control must withdraw Pay mid-flow), the server total can change (A-02 must re-run with a method already selected), the app can be backgrounded (the return-from-another-app rule: nothing confirms on return), and a double press can race the confirm. Every one of those is a payment-flow ordering `payControl` governs, and each needs its own test matrix and a D negative-control round — for a display card. The owner's instruction: do not introduce a payment-flow change merely to reproduce a design card.

Recommendation: (a) keep the single-step sheet; (b) if the card must show the method before presenting, source it read-only — the saved default from the `customerId`/ephemeral key the intent response already returns (a read, no change to when the charge happens) — and label it "Default card" with the sheet still allowed to change it; (c) if that read is not acceptable, drop the card. If the owner still wants FlowController, it is a separate stop-and-ask package with: the four scenarios above as tests, `payControl` extended with a `method_selected` state, and A + D review before any candidate build.
