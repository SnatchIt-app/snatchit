### 1. MAJOR — Phase-2 row shape (`payments.listing_id`/`seller_id` NULL, `mode='native_primary'`) breaks four new paths

Production carries 093 (`/Users/josetascon/snatchit-consol/supabase/migrations/093_primary_ticketing.sql:3025-3026` drops both NOT NULLs; `:3003-3006` widens `mode` to include `native_primary`; `payments_rail_pairing_ck` forces `listing_id IS NULL AND seller_id IS NULL` exactly when `mode='native_primary'`). None of the three reviewed migrations is aware of that shape. Reproduced on the rehearsal DB after applying the same DDL (`fin_scenarios2.sql` S1):

a. **`guard_payment_transitions` party-only branch is NULL-hostile — `delete_account_cleanup` raises.** `M3:392-403`: `v_party_only := … AND NEW.seller_id = OLD.seller_id … AND NEW.listing_id = OLD.listing_id …` — with either column NULL the conjunction is NULL, the bypass branch is skipped, and the identity-freeze check (`M3:422-433`) raises `payments money/identity columns are immutable once succeeded`. S1d: `delete_account_cleanup(other_user)` on a user whose only payment is a *refunded* `native_primary` row → `ERROR … immutable once succeeded (20260906120000)` from `update public.payments set buyer_id = v_sentinel_id` (0563 body). S1e: same raw statement with `app.bypass_transfer_guard=on` raises; S1f control on a resale row lives. Effect: every account deletion of a user holding any succeeded/refunded venue-direct payment 500s at the cleanup step (`delete-account/index.ts:263-270`), forever, and the deletion ledger sits at `archived`.
   Fix: use `IS NOT DISTINCT FROM` for `seller_id`, `listing_id`, `buyer_id` comparisons in `v_party_only` (and allow `NEW.seller_id IS NULL AND OLD.seller_id IS NULL`).

b. **`account_deletion_blockers.paid_no_transfer` blocks native buyers permanently.** `M3:851-856` flags every `succeeded` payment with no `transfers` row; venue-direct payments never have one. S1c: `paid_no_transfer` returned for the native succeeded row → 409 on every deletion attempt, no operator path clears it.
   Fix: scope the `paid_no_transfer`, `pending_payment` and `unresolved_review` arms to `p.mode IN ('buy_now','auction')` (or `p.listing_id IS NOT NULL`); native obligations are owned by `kernel.*`.

c. **`get_unsettled_payments.pending_stale` lists native pending rows and `settle_verified_payment` raises on them.** `M2:364-371` has no listings join; S1a returns the native pending row as `pending_stale`. The sweep then re-fetches the PI and calls the contract; `M2:301` → `settle_listing_for_payment` → `M1:121-122` `RAISE 'Listing not found.'` (S1b). Same raise for an already-succeeded native row (S1b2) — i.e. if this branch's `stripe-webhook` is deployed as-is, every native-rail `payment_intent.succeeded` returns 500 (`W:299-302`) and Stripe redelivers for 3 days; the sweep logs `reconciled_errors` every run for the row's 2h window. Note the *production* webhook (`snatchit-consol/supabase/functions/stripe-webhook/index.ts:752-754`, `native.ts:115 resolveRail`) dispatches on `metadata.rail` before the legacy arm; the branch webhook (913 lines vs 1791) has no dispatch — a deploy of the branch file regresses Phase-2 handling (`04_RELEASE_PLAN.md:10` already records "production edge code is ahead of main").
   Fix: `get_unsettled_payments` add `p.listing_id IS NOT NULL` to `pending_stale`; `settle_verified_payment` return a new terminal outcome (e.g. `not_resale`) or `binding_mismatch` when `v_p.listing_id IS NULL`, before step 5; rebase the webhook/delete-account edges onto the production versions before P3-d.

d. `settle_verified_payment` binding (`M2:190-192`) and `cleanup_expired_reservations` are NULL-safe (`v_meta_listing::uuid <> NULL` is NULL → no mismatch); `claim_payout_attempt` is unreachable for native rows (no transfer). No new FK/index in the three migrations conflicts with the nullable columns (`payout_attempts.payment_id` FK only; `idx_payments_one_success_per_listing` unchanged, NULLS DISTINCT).

### 2. MAJOR — Full refund *after* payout is never flagged for reversal (asymmetric with dispute-lost)

`W:651-705` (`charge.refunded`) records refunds through `record_payment_refund` and returns; unlike `charge.dispute.closed` (`W:623-643`) it never checks whether the transfer was already paid and never calls `flag_payout_reversal_required`. `record_payment_refund` (`M3:527-616`) likewise flips the payment to `refunded` without looking at `transfers`. Reproduced (S6): transfer B auto-released → attempt recorded `succeeded` with `tr_paid` → `record_payment_refund(…11000,'dashboard')` → payment `refunded`; attempt state still `succeeded`; `payout_decisions` for B = 0; `account_deletion_blockers(seller)` has no row for B/its attempt (settled := `payout_released_at IS NOT NULL`, `M3:833-835`). The platform has returned 11 000 to the buyer from its own balance while the seller keeps 9 000, nothing surfaces it, and the seller can delete their account (Connect id survives only on `account_deletions.connect_id`).
Scenario: ops (or Stripe Radar early-fraud refund) refunds a charge days after auto-release; today the only trace is the Stripe dashboard.
Fix (DB side, covers every caller): in `record_payment_refund`, after the UPDATE, `IF v_pay.status = 'refunded' THEN PERFORM public.flag_payout_reversal_required(t.id, 'REFUNDED_AFTER_PAYOUT', jsonb_build_object('stripe_refund_id', p_stripe_refund_id)) FROM transfers t WHERE t.payment_id = v_pay.id AND (t.payout_released_at IS NOT NULL OR t.stripe_transfer_id IS NOT NULL)`. (`flag_…` is already idempotent per reason code and is what makes `open_manual_review` block deletion, `M3:895-903`.) Reason `'dispute_lost'` should also skip when source is `expiry`/`unfulfillable` (those never have a paid transfer, harmless either way).

### 3. MINOR — Seller payout amount ignores partial refunds/chargebacks on the DB side; the only cap is a Stripe pre-flight that does not see chargebacks

`claim_payout_attempt` freezes `amount_cents = v_p.amount − seller_fee` (`M3:717-720`) with no reference to `payments.amount_refunded_cents`. S3: after a 5 000 partial refund on an 11 000 charge the claim freezes 9 000 although only 6 000 remains retained. Protection is only `createSellerPayout` pre-flight `sellerNetCents <= maxTransferableCents(charge.amount, charge.amount_refunded)` (`P:153-167`, `L:129-131`) plus Stripe's own `source_transaction` ceiling. Consequences:
- Partial refunds up to the platform's gross fee (20% of base) are silently funded by the platform (9 000 payout on 6 000 retained fails pre-flight; a 1 500 goodwill refund passes and the platform nets 500). Ratified as "a partially refunded charge still settles", but the payout side of that decision — who absorbs the refund — is undocumented; it should be explicit in `06_PAYMENT_FLOW.md`.
- `charge.amount_refunded` excludes lost disputes. S11: a partial chargeback of 4 000 (`record_payment_refund(…,'dp_partial',4000,'dispute_lost')`) leaves the payment `succeeded` and, if the transfer was never frozen (dispute created before the transfer existed — round-1 NOTE-7 — or the freeze failed, see F5), the claim still freezes 9 000 and the pre-flight passes (`ch.refunded !== true`, `amount_refunded` 0). Platform pays 9 000 on a charge that retained 7 000. It is caught later only by `flag_payout_reversal_required` on `dispute.closed lost`, which in this ordering has already fired (the dispute closed before payout) — so nothing flags it.
Fix: in `claim_payout_attempt` add `IF v_amt > v_p.total − coalesce(v_p.amount_refunded_cents, 0) THEN RAISE EXCEPTION 'PAYOUT_EXCEEDS_RETAINED'` (add to `PAYOUT_NOT_ELIGIBLE_REASONS` in `P:270-273` → manual review), and in the pre-flight also refuse when `ch.disputed === true` (Stripe charge field) unless `transfers.dispute_resolution = 'resolved_seller_paid'`.

### 4. MINOR — `settle_verified_payment` ledgers the *cumulative* refunded amount under the *latest* refund id; `payment_refunds` (append-only) overstates

`M2:243-244` passes `least(p_amount_refunded, v_p.total)` (the charge's cumulative `amount_refunded`, `C:275`, `E:311`) together with `refunds.data[0].id` (`C:276`, `E:312`). S2: prior partial `re_1`=5 000 via `charge.refunded`, then the contract sees `amount_refunded`=11 000 with `data[0]='re_2'` → inserts `re_2`=11 000 (true value 6 000); the later true `charge.refunded` for `re_2` is `ON CONFLICT DO NOTHING`; `sum(payment_refunds.amount_cents)` = 16 000 > total. `payments.amount_refunded_cents` stays correct only because of the `least(...,total)` cap (`M3:594`). The ledger is append-only, so the misstatement is permanent, and `stripe_refund_id` on `payments` ends up `re_1` while the row's "full refund" reference is `re_2`.
Fix: pass the increment (`p_amount_refunded − coalesce(v_p.amount_refunded_cents, 0)`) or, better, have the edges pass the refund list and loop `record_payment_refund` per refund with each refund's own `amount` (exactly what `W:681-696` already does).
Related NOTE: `source` for the same refund id is caller-order dependent (`W:683` labels an unfulfillable refund `'expiry'` because its metadata `source` starts with `enforce-transfer-expiry`; the sweep labels it `'unfulfillable'`) — cosmetic, but use `metadata.reason` to disambiguate.

### 5. MINOR — Dispute freeze that fails is acknowledged; and the claim→POST window has no last-moment re-check

a. `W:469-484`: `freeze_transfer_for_dispute` error → `console.error` only, then the dispute upsert → `markProcessed()` (`W:523`). A transient DB error leaves `disputed_at` NULL with the event terminal; `claim_payout_attempt` then sees no dispute (`M3:690-692`) and pays. This is the F06 pattern still present in the one branch that gates payouts. Fix: `return await finish(false, …)` on `freezeErr` (same as the upsert failure at `W:515`).
b. `mark_payout_requested` (`M3:735-747`) only checks `state='claimed'`. S8: claim → `freeze_transfer_for_dispute` → `mark_payout_requested` returns `true` → recorded `reversal_required`/`PAID_DURING_DISPUTE`. The design accepts PAID_DURING_DISPUTE as a compensation state, but the window includes two Stripe GETs (~1–2 s per attempt, `P:123,142`) that a cheap re-check would close. Fix: in `mark_payout_requested`, `UPDATE payout_attempts a SET … FROM transfers t WHERE t.id = a.transfer_id AND a.id = $1 AND a.state='claimed' AND t.payout_released_at IS NULL AND (t.disputed_at IS NULL OR t.dispute_resolution = 'resolved_seller_paid')`; on `false` the edge already returns `not_requested` → attempt closes as `failed` on the next sweep (`P:399-403`). Better still, record `failed_not_created` immediately in that branch instead of leaving the lease to expire.

### 6. MINOR — Late captures (> 2 h after PI creation) with a lost webhook are never reconciled; buyer charged, nothing owed in the ledger

`get_unsettled_payments.pending_stale` is bounded to `created_at` 15 min … 2 h (`M2:370-371`, round-1 MINOR-5). A PaymentIntent confirmed > 2 h after minting (PaymentSheet left open; the client_secret does not expire and `create-payment-intent` reuses the pending PI, `create-payment-intent/index.ts:560-640`) whose `payment_intent.succeeded` was lost and whose `confirm-payment` failed/never ran stays `pending` forever: not on the work list, no review row, and after 24 h not a deletion blocker either (`M3:858-866`). Money captured, no fulfilment, no compensation, no signal. Fix: add a low-frequency wide arm (e.g. `pending` rows 2 h … 7 d, priority 5, at most N per run, or gated by a new `reconcile_after` timestamp with exponential backoff), or scan `stripe_webhook_events` rows with `processed_at IS NULL` older than 1 h as a second work list.

### 7. NOTE — Deploy-window double payout between legacy `record_transfer_payout` callers and the attempt protocol

`record_transfer_payout(uuid,text)` (0564) is deliberately kept (`M3:37-40`). During P3-d, if the still-deployed `enforce-transfer-expiry` v36 (key `payout_<id>`) and the new `confirm-and-release` (key `payout_<id>_a1`) both act on one `buyer_confirmed`/`auto_released` row, two real transfers are possible. If the legacy write lands first, the new attempt is recorded `DUPLICATE_TRANSFER` (S9 shows this detection works: attempt 1 `reversal_required` with `tr_1`, transfer keeps `tr_2`, review row written). If the new write lands first, `record_transfer_payout` returns false and the legacy edge logs "already released" — the legacy `tr_` id is lost (old F07). Mitigation: pause the cron (`cron.alter_job(active := false)`) for the duration of P3-d, and run the MINOR-4 pre-enable query already in `M3:105-124`.

### 8. NOTE — Operator-only compensation states (money held, no automatic path)

`binding_mismatch` and `unknown_payment` (`M2:154-165, 194-208`) hold captured money with no automatic refund; the row stays `pending`, the listing is re-listed by `cleanup_expired_reservations` (no succeeded payment) and can be re-sold. Deletion is blocked (`unresolved_review`, round-1 MAJOR-1), so nothing is lost, but there is no alert: add a `captureException` once per new review row in the sweep (it currently `continue`s silently at `E:347-352`) and an ops runbook line. `unknown_payment` dedupe runs under no lock (round-1 NOTE-6) — harmless.

### 9. NOTE — `reversal_required` is terminal; a dispute later *won* leaves the attempt and decision open

`M3:263-268` allows only `succeeded → reversal_required`. After PAID_DURING_DISPUTE + `charge.dispute.closed won`, the transfer stays `disputed`, the attempt stays `reversal_required`, and `open_manual_review` + `open_payout_attempt` block deletion until an operator inserts a `release` decision *and* the transfer is `reversed` — but a won dispute should not be reversed. `account_deletion_blockers` arm `M3:906-911` only clears on `transfers.status='reversed'`. Fix: clear the `reversal_required` arm when a later `payout_decisions.decision='release'` exists for the transfer (mirror the `open_manual_review` arm), or when `resolve_dispute(...,'seller_win')` has stamped `dispute_resolution='resolved_seller_paid'`.
