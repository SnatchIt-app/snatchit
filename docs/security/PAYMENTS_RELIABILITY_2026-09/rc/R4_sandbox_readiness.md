**Headline.** The RC's money-OUT rails are structurally inert under a Stripe **test** key: `create-payment-intent` records
`payments.stripe_livemode = PI.livemode` (`supabase/functions/create-payment-intent/index.ts:771`), and every payout /
sweep path refuses `stripe_livemode <> true`:
`claim_payout_attempt` → `PAYMENT_NOT_LIVE` (`supabase/migrations/20260906120000_…:631-632`);
`createSellerPayout` pre-flight `pi.livemode === true` (`supabase/functions/_shared/payouts.ts:163`);
`get_unsettled_payments` drops `stripe_livemode = false` rows (`20260906110000_…:409`);
Phase 1 expiry refund `rowIsLiveActionable` (`enforce-transfer-expiry/index.ts:510`, `_shared/payout-logic.ts:150`);
Phase 1b `.eq('payments.stripe_livemode', true)` (`enforce-transfer-expiry/index.ts:669`).
A sandbox run therefore proves checkout → settlement → webhook → refund/dispute **sync** end to end, but can NOT prove a
real `POST /v1/transfers` from `confirm-and-release` / `enforce-transfer-expiry`, nor Phase 0/1/1b sweeps, without either
(a) a service-SQL flip of the row to `stripe_livemode = true` (which still fails at the Stripe pre-flight → attempt
`failed` with `PAYOUT_SOURCE_CHARGE_UNAVAILABLE`), or (b) a live-mode smoke on production after deploy. Owner decision
(§4 G1). Everything else below is runnable.

## 4. Gaps — mocked assertions a real run could contradict, and what is untested

**G1 (blocker for the payout rows).** Live-mode gate. Mocks and pgTAP fixtures set `stripe_livemode=true` (`122_payout_attempts.sql:18`, `payout-protocol.ts` PI probe `livemode: true`, rehearsal seed `UPDATE payments SET stripe_livemode = true`). Real test-mode rows are `false` ⇒ `claim_payout_attempt` `PAYMENT_NOT_LIVE` (`20260906120000_…:631`), `createSellerPayout` `source_charge_unavailable` (`payouts.ts:163`), `get_unsettled_payments` excludes (`…110000:409`), Phase 1/1b skip (`enforce-transfer-expiry:510,669`). ⇒ `POST /v1/transfers` from the RC edges, the legacy-orphan pre-flight against real listings (`payouts.ts:261-294`), `source_transaction` semantics, and the Phase 0 sweep are provable ONLY live. Options: (a) accept mocked + `122`/`payout-races` coverage and do a $1 live smoke on production after P3-d (one buy-now, seller confirm, `payout_attempts` row, `stripe transfers list --transfer-group`); (b) a sandbox-only env switch is NOT in the RC and would test different code — do not add for this release. Owner decision.

**G2.** Cron URL/secret coupling: `032:100`, `033:209`, `099:233,238` hard-code the production host; a sandbox that replays them without P0.3 either never sweeps or POSTs to production (401 by `enforce-transfer-expiry:165-176`; `notify-report` auth similar). Not a production risk; a sandbox-fidelity risk.

**G3.** Stripe account hygiene: a test-mode endpoint already exists on the production Stripe account (`08_…`: "Do NOT touch the test-mode endpoint"); its URL/secret are not in the repo. Running test-mode traffic on that account may deliver to whatever it targets. Use a Stripe Sandbox (separate `sk_test_`), or disable that endpoint for the run and re-enable after.

**G4.** Mobile SDK ↔ ephemeral key version: server pins `2024-04-10` for `/ephemeral_keys` (`_shared/stripe.ts:35`, `create-payment-intent:199-203`) against `@stripe/stripe-react-native 0.50.3`; only a device proves PaymentSheet decodes it (saved-card UI). Mocks never validate the version string.

**G5.** Webhook payload shape depends on the ENDPOINT api_version, not the server pin: mocks hand-build events (`settlement-webhook.test.ts`, `refund-dispute-webhook.test.ts`) with `refunds` omitted/present as the test chooses; real `charge.refunded` under `2024-09-30.acacia` omits `charge.refunds` ⇒ the expand fetch (`stripe-webhook:676-685`) runs on every refund event (one extra GET per delivery, Stripe rate limits). `charge.dispute.created.payment_intent` presence and `dispute.status` label set (`disputes` CHECK-less `status text`) are only proven live. Create the sandbox endpoint with the same `api_version` as production's live endpoint (verify with `stripe webhook_endpoints retrieve`).

**G6.** `payment_intent.payment_failed` on a still-live PI (buyer retries in-sheet): the RC marks the row `failed` and RELEASES the Buy-Now hold (`stripe-webhook:369-412`) while the same PI can still succeed seconds later (`failed → succeeded` allowed, `20260906120000_…:396`; `settle_listing_for_payment` settles a released listing, `…100000:157-158`). A competing buyer who reserves in that gap is then refused at mint by "sold in fact" only AFTER the success lands (`create-payment-intent:433-453`) — the window between release and success is real and untested by mocks (S3 measures it). Also the cancel-refusal regex (`:275`) is matched against Stripe's real error text — record it in S4.

**G7.** Idempotency-key semantics: mocks model Stripe's 24 h key TTL and "same key, different params ⇒ 400" (`tests/helpers/payout-protocol.ts` `createTransfer`); real Stripe also scopes keys per API version header and returns the ORIGINAL response (including a `canceled` PI — handled `create-payment-intent:721-733`). The customer-id salt (`:689-691`) and the `_r<n>` failed-attempt salt are only proven by S1.2/S4 replays.

**G8.** Connect event routing: `account.updated`, `payout.paid`, `payout.failed` for Express accounts arrive only via a Connect (`connect=true`) endpoint; the handler reads `event.account` (`stripe-webhook:796,808`). The 08 doc describes ONE live endpoint with all 11 events and the handler verifies ONE secret (`:8`, `:73-`). If production's endpoint is not Connect-typed, `profiles.stripe_charges_enabled/…` are refreshed only by `create-connect-account status_only` calls (`create-connect-account:262-291`) and payout.* branches are dead. Verify on the production Stripe account (read-only `stripe webhook_endpoints list`), then mirror in the sandbox. Two endpoints would need two secrets — unsupported by the handler.

**G9.** Deletion sweep has no grace window (`078_…:1696-1705`): a clean identity is tombstoned on the next 2-minute tick after request. The client contract (`app/settings/index.tsx`) and 09 §3 assume a grace period exists; untested by any suite because `125` calls the sweep directly. Confirm intended.

**G10.** Time windows are only reachable by backdating in a sandbox: reservation 10 min, `pending_stale` 15 min–2 h (`…110000:400-401`; MINOR-6 open), expiry 24 h, auto-release 72 h, lease 10 min (`…120000:585-588,739`). Backdating needs the guard-bypass GUCs (2.6); production never runs these paths for hours/days after deploy — first-24 h observation (`04_…` §5) is the real proof.

**G11.** Rate limiter as a test hazard: scripted S-steps exceeding `check_rate_limit` windows return 429/503 (fail-closed) and can be mistaken for defects; `reserve_buy_now` limit is INSIDE the RPC (`…100000:324`).

**G12.** Build 13 cannot be pointed at the sandbox (production profile hard-codes the prod URL; `eas.json`); its compatibility with the four migrations is proven only by pgTAP `120`/rehearsal §E and by a post-deploy live smoke. The web client (`web/src/lib/checkout.ts:127` reads `stripe_verified`) is outside this matrix.

**G13.** Legacy pre-flight breadth: `findTransferByLegacyMetadata` reads ≤3×100 recent transfers per destination (`payouts.ts:265-292`); a seller with >300 transfers since the obligation's `created_at-24h` window could hide a legacy orphan ⇒ a second POST. Untested (mock lists everything). Production sellers are far below this today (`044` comment: 7 live Connect accounts).

**G14.** `transfer.created` overwrites `payout_attempts.error` with `{source:'webhook:transfer.created', …}` via `error = coalesce(p_error, error)` (`…120000:796`) when the edge already recorded — minor evidence loss; no test asserts the JSON after the webhook replay.
