## Findings

**MAJOR-1 — paid-but-unsettled inventory is re-reservable / released by `reserve_buy_now` (I2/I3 premise broken).** `M:257-258` (pre-sweep) and `M:288-289` (cross-listing release) act on `listings` state only; a listing with a `succeeded` payment that the webhook/client has not yet settled (webhook lag, retry loop) is handed to another buyer, who then passes `cpi:384-389` and mints a live PI → second capture. Repro (scratch `adv_reservation.sql`): R1 other_user `reserve_buy_now` on a lapsed-hold listing with a succeeded payment → **no exception, reserved_by flips**; R2b/R2c buyer reserving a second listing **releases** its own paid hold and other_user takes it. Contradicts `M:27-31` ("that holder cannot have paid") and the decision-1 premise; also inconsistent with Package 2's ratified "`cleanup_expired_reservations` skips paid listings" — P1's inline sweep would undo P2's guard. I3 still holds (one success index + core's transfer check → one fulfilled sale) but the outcome is a compensation refund instead of prevention. Fix: in `reserve_buy_now` raise `'This listing has already been sold.'` when `EXISTS (payments WHERE listing_id=p_listing_id AND status='succeeded')`, exclude such rows from both UPDATEs (`AND NOT EXISTS (...)`), and add the same refusal to `cpi` (both branches) for a succeeded payment by another buyer.

**MAJOR-2 — decision-3 retirement misses the most common expired path.** `cpi:378-383` returns 400 before `refuse()` (`cpi:368`) whenever `status !== 'reserved'`. After `cleanup_expired_reservations` (cron `*/2`) flips a lapsed hold to `active`, the lapsed holder's `pending` PI is *not* cancelled — the retirement only fires in the ≤2-minute window where `status='reserved'` and `reserved_until` is past. Repro: scratch vitest X1 → `expected [] to equal ['/payment_intents/pi_stale/cancel']`. Same for `status='sold'` in the Buy-Now branch. Fix: `return refuse(400, 'Listing is not reserved for purchase', 'not-reserved')` (keep message/status for shipped clients).

**MAJOR-3 — retirement is lazy: other buyers' stale secrets survive a mint.** `retireStalePendingIntents` (`cpi:218`) is called only when *the same buyer* is refused. Holder H mints PI (pending), lapses, never calls cpi again; C reserves and mints; H confirms the still-live secret → capture → webhook promotes H → `mark_listing_sold(H)` settles (money wins) → C's capture collides (23505 → 500 loop until P2). Repro: scratch vitest X3 (holder mint, `pi_other` pending) → no cancel. Fix: when minting/reusing for the live holder, cancel every *other* buyer's `pending` PI on the listing (same helper without the buyer filter, `neq('buyer_id', buyerId)`), best-effort, before returning the secret. Also recommend `payment_intent.canceled → release_reservation` in the webhook (investigation §4.3; B-owned, not P1).

**MINOR-4 — I1 amount binding on the reuse path (pre-existing, not closed).** `cpi:502-551` returns the existing pending PI's `client_secret` without comparing `existingPiData.amount/currency` to `totalCents`; 072's header records that sellers can re-price on UPDATE. Repro: scratch vitest X2 (price 200→300, PI minted at 22000) → 200 with `clientSecret: pi_old_secret, total: 33000`: buyer is charged 22000 while the UI shows 33000. Low exploitability (only the seller can move price). Fix: on reuse, if `amount !== totalCents || currency !== 'usd'` cancel + retire (`failedAttempts++`) and mint fresh.

**MINOR-5 — deadlock exposure inside `reserve_buy_now`.** `M:288-289` locks the caller's other holds in scan order after locking the target (`M:262`). Same-buyer double-tap on two listings (T1: lock L2 → wants L1; T2: lock L1 → wants L2) or two buyers swapping lapsed holds deadlocks; PG resolves with 40P01, surfaced raw via `ListingDetailScreen:784` / `web/src/lib/checkout.ts:68`. Acknowledged in `M:57-59`. Fix: `SELECT id FROM listings WHERE id = p_listing_id OR (reserved_by = caller AND status='reserved') ORDER BY id FOR UPDATE` once, before any write. Cross-table order is consistently payments→listings (core `M:94/100`, wrappers `M:172-179/207-220`); `ensure_transfer_exists` (061) takes no row locks; `cleanup_expired_reservations`/`cancel_listing` touch listings only — no cross-table cycle found.

**NOTE-6** — Hold is renewable indefinitely in 10-minute slices: lapsed holder re-reserves and gets a fresh window (scratch R5/R5b pass); rate limit 20/600 s never binds at 1 call/10 min. Within decision 2's letter; flag for the lead (per-listing re-reserve cap if undesired).
**NOTE-7** — Money wins over an ended auction with a *different* winner: a succeeded `buy_now` payment marks it sold and locks the winner out (scratch R6 passes). Consistent with decision 1, but not stated anywhere; the winner's minted auction PI then stays confirmable (MAJOR-3 class).
**NOTE-8** — New refusals return 409 where the old ones returned 400; clients parse the body (`src/lib/payments.ts:80-93`), fine. `metadata[reserved_until]` (`cpi:587-591`) is forensic-only, not in the ratified list — harmless scope; changes the PI body for first-attempt keys only (no idempotency collision since prior mints are reused, not re-POSTed).
**NOTE-9** — `complete_auction_payment` called by the webhook (service_role) raises while a foreign hold is live → `finish(false)` → Stripe retries ≤10 min. Acceptable until P2.
**NOTE-10** — `search_path='public'` (not `public, pg_temp`) matches the 0590 convention; §8-tolerated.
