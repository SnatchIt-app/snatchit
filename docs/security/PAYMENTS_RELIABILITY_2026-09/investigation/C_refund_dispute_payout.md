## 3. Smallest durable recovery: `payout_attempts`

```sql
CREATE TABLE public.payout_attempts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  transfer_id uuid NOT NULL REFERENCES transfers(id), payment_id uuid NOT NULL REFERENCES payments(id),
  attempt_no int NOT NULL, state text NOT NULL CHECK (state IN ('claimed','requested','unknown','succeeded','failed','reversal_required')),
  destination text NOT NULL, amount_cents int NOT NULL CHECK (amount_cents>0), currency text NOT NULL DEFAULT 'usd',
  source_charge_id text, idempotency_key text NOT NULL UNIQUE,          -- payout_<transfer_id>_a<attempt_no>
  stripe_transfer_id text UNIQUE, actor text NOT NULL, error jsonb,
  claimed_at timestamptz NOT NULL DEFAULT now(), requested_at timestamptz, resolved_at timestamptz,
  lease_expires_at timestamptz NOT NULL, UNIQUE (transfer_id, attempt_no));
CREATE UNIQUE INDEX payout_attempts_one_open ON payout_attempts(transfer_id) WHERE state IN ('claimed','requested','unknown');
CREATE UNIQUE INDEX payout_attempts_one_success ON payout_attempts(transfer_id) WHERE state='succeeded';
CREATE UNIQUE INDEX transfers_stripe_transfer_id_uniq ON transfers(stripe_transfer_id) WHERE stripe_transfer_id IS NOT NULL;
-- BEFORE UPDATE trigger: destination/amount/currency/idempotency_key/source_charge_id immutable; state may only advance.
```
Key is per-attempt, not destination-salted: recovery always replays *that attempt's* frozen params. A new attempt opens only after the previous is terminal.

RPCs (SECURITY DEFINER, service_role only, no network inside):
- `claim_payout_attempt(p_transfer_id uuid, p_actor text, p_lease interval DEFAULT '10 min') RETURNS TABLE(attempt_id, attempt_no, idempotency_key, destination, amount_cents, source_charge_id, payment_intent_id, needs_reconcile bool)` — `FOR UPDATE` on transfers; requires status ∈ {buyer_confirmed, auto_released}, `(disputed_at IS NULL OR dispute_resolution='resolved_seller_paid')`, `payout_released_at IS NULL`, `payments.status='succeeded' AND stripe_livemode`; snapshots destination from profiles and amount from payments; if an open attempt exists → returns it with `needs_reconcile=true` (never inserts a second).
- `mark_payout_requested(p_attempt_id)` — claimed→requested, called immediately before the POST.
- `record_payout_attempt_result(p_attempt_id, p_stripe_transfer_id text, p_outcome text /*succeeded|failed_not_created|unknown*/, p_error jsonb)` — on `succeeded` **always** writes `transfers.payout_released_at/stripe_transfer_id` (money already moved; refusing is F07) and, if `disputed_at IS NOT NULL`, sets state `reversal_required` + inserts `payout_decisions` manual_review `PAID_DURING_DISPUTE`. `unknown` extends the lease.
- `reconcile_payout_attempt(p_attempt_id, p_found_transfer_id text)` — same write path when a search found it; `failed` when the caller proves none exists.

Edge order (both callers, replacing 434–579 / 543–701): 1 claim (short tx) → if `needs_reconcile`: `GET /v1/transfers?transfer_group=<transfer_id>` (send `transfer_group` + `metadata[attempt_id]` on the POST), match `metadata.attempt_id`, reconcile, **stop — no POST this run**. 2 pre-flights (Stripe GETs, no DB locks). 3 `mark_payout_requested`. 4 POST with attempt key + frozen destination/amount (never re-read profile). 5 record: 2xx→succeeded; definite non-idempotency 4xx→failed_not_created; network/5xx/409-in-flight→unknown. Buyer response after claim = `payout_status:'processing'`; `already_released` only when a `succeeded` attempt exists. `transfer.created` webhook calls `record_payout_attempt_result` from `metadata.attempt_id` (idempotent via unique `stripe_transfer_id`). Phase 2b becomes "attempts with expired lease" + "eligible transfers with no attempt".

Rollback: drop the three indexes/table/RPCs; redeploy confirm-and-release v34 / enforce-transfer-expiry v36 (`record_transfer_payout` is untouched, so old edges keep working). Pre-flight before the unique index: `SELECT stripe_transfer_id, count(*) FROM transfers WHERE stripe_transfer_id IS NOT NULL GROUP BY 1 HAVING count(*)>1` must be empty. Interfaces needed from A/B: monotonic `payments.status` (§4); ideally `payments.stripe_charge_id` populated at settlement so the claim can freeze `source_charge_id` without a Stripe GET.

## 4. Refund-state monotonicity

Additive DDL: `payments.amount_refunded_cents int NULL` (NULL = legacy/unknown; never backfilled), append-only `payment_refunds(id, payment_id, stripe_refund_id UNIQUE NULL, stripe_dispute_id NULL, amount_cents, source CHECK IN ('expiry','dispute_lost','dashboard','admin'), created_at)`. Trigger `guard_payment_transitions` BEFORE UPDATE ON payments (bypass GUC `app.bypass_payment_guard` for ops, cleared by a statement trigger as in 0563): allowed status moves pending→processing|succeeded|failed, processing→succeeded|failed, failed→succeeded, succeeded→refunded; everything else RAISE — explicitly `refunded→*`. `amount/buyer_fee/seller_fee/total/stripe_payment_intent_id` immutable once `succeeded` (closes 060 F-3); `refunded_at`/`stripe_refund_id` non-null→different non-null RAISE; `amount_refunded_cents` non-decreasing, ≤ `total`. Going forward: `charge.refunded` → insert `payment_refunds` per `charge.refunds.data` (fetch if absent), set `amount_refunded_cents = charge.amount_refunded`, status `refunded` only when `charge.refunded === true`; dispute lost → `payment_refunds(source='dispute_lost', stripe_dispute_id, amount=dispute.amount)`, status `refunded` only when amount == total, and if the transfer is paid → attempt state `reversal_required` + manual_review `DISPUTE_LOST_AFTER_PAYOUT`. Interface for Agent B: `payment_intent.succeeded` claim must use `NOT IN ('succeeded','refunded')` (the trigger would otherwise raise → `finish(false)` → Stripe retries for 3 days); `confirm-payment:216` needs `.eq('status','pending')`-style predicate.

## 5. Account deletion

Gate RPC `account_deletion_blockers(p_user_id) RETURNS TABLE(kind text, ref_id uuid)` (service_role); edge returns 409 with kinds, and **503 on any query error**. Blockers: transfers where user is a party and NOT settled, settled := `payout_released_at IS NOT NULL` OR `(payments.status='refunded' AND coalesce(amount_refunded_cents,total)=total)` — this catches pending/seller_sent/disputed/buyer_confirmed-unpaid/auto_released-unpaid/expired-unrefunded/reversed; payments `pending|processing` < 24h old or `succeeded` with no transfer row; `disputes.status` not in (won,lost,warning_closed,charge_refunded); open `payout_attempts`; open manual_review decisions with no later release. Block, don't tombstone, while obligations exist. After the gate: tombstone (current sentinel approach) but preserve `stripe_payment_intent_id`, `stripe_refund_id`, `stripe_transfer_id`, `payout_attempts.destination` (already immutable), `disputes`, and write `stripe_connect_archive(profile_id, stripe_connect_id, reason='account_deleted')` before the profile cascades; anonymize `payout_decisions` parties too. Restartable: `account_deletions(user_id, phase, connect_id, started_at, finished_at)`; phases gate→archived→cleaned→storage→auth→done; retry resumes from the recorded phase and never re-runs the gate after `cleaned`; auth delete failure leaves `phase='storage'` and a pg_cron/sweep finishes it. Flag: listing/checkout RPCs should refuse users with an open `account_deletions` row.

## 7. Corrections to the audit text

- F07 line refs are right; the window is wider than "reads then POSTs" — two Stripe GETs (`payouts.ts:82,103`) sit inside it. The DB does not merely "omit the provider transfer id": status stays `disputed` and the 9b audit insert is skipped, so the id is nowhere in the DB. The sweep's `disputed_at IS NULL` filter (797) means F07's orphan is invisible to F08's recovery until a seller-win, at which point F08(d)/(e) fire — the two findings compound.
- F08: "recovery can use a different destination/key" only if `profiles.stripe_connect_id` changed; the >24h double-pay (d) happens with an unchanged destination too. `(f)` concurrent releasers is not a double-pay today.
- F05: overstates the pure full-refund → payout risk (`payouts.ts:126` blocks it at Stripe truth) and understates dispute-lost, where the charge is *not* refunded and a status regression pays out. `charge.dispute.closed` lost writes no refund id/amount — it is a chargeback, not a refund, and should never populate `stripe_refund_id`.
- F10: the cleanup RPC itself is atomic (0563); partial completion is between cleanup and auth delete. "Destination from current profile" understates it: after deletion the profile is cascade-deleted, so the obligation is unpayable, not misdirected. Also `payout_decisions`/`disputes` are not anonymized.
- Not in the audit: `docs/operations/DAY5_MANUAL_REFUND_PLAYBOOK.md` Part 2 Step 3 (direct `UPDATE transfers SET payout_released_at…`) is blocked by the guard since 0562; ops must use `record_transfer_payout`, and the playbook's manual dashboard transfer is the (c)→double-pay path.
